# 阶段 2：收敛

你已完成探查（快速路线）或探查+发散（深潜/围猎路线）。现在的任务是将信息收敛为一份可以写入 Spec 的需求定义。

**完成本阶段并获得用户确认之前，不要读取 `spec-write.md`。**

---

## 信息基础

根据你走的路线，你手上有不同级别的信息：

- **快速路线**：只有探查阶段的粗粒度地图
- **深潜路线**：工作目录中的 `findings.md`
- **围猎路线**：工作目录中的 `findings-final.md`

后续每个步骤都应利用已有的信息——不要重复收集已经知道的东西，也不要忽略已经发现的事实。

---

## 步骤 1：Scope 预判

这是一件事还是多件独立的事？

- 如果用户说"做一个面板系统+数据绑定+权限控制"→ 多件事，先拆成子项目
- 如果用户说"给编辑器加个搜索功能"→ 一件事，继续

**大需求的处理**：
1. 列出识别到的独立子项目
2. 建议处理顺序（依赖关系、优先级）
3. 与用户确认后，对第一个子项目继续本流程
4. 每个子项目走独立的收敛 → Spec → /todo 周期

## 步骤 2：聚焦提问

**一次只问一个问题。** 等用户回答后再问下一个。一次多个问题会导致用户只回答最容易的那个，跳过需要思考的——而需要思考的往往最关键。

**尽量用多选题。** 能给选项就给选项——基于代码库上下文和发散发现生成的选项，往往能覆盖用户没想到的方向。开放式问题留给真正需要自由表达的地方。

### 快速路线升级检查

如果你走的是快速路线，在开始提问前先检查：探查时认为涉及 ≤2 个模块，现在还是这样吗？如果在提问过程中发现了新的模块或跨模块依赖，暂停提问，建议用户升级到深潜路线。

### 跳过已回答的问题

发散阶段已经回答的问题直接跳过——不要为了走流程而重复提问。但发散阶段发现的歧义点和决策点，必须问。

### 需求类型分流

判断需求类型，选择对应的提问框架：

**新功能**——核心维度：
- 用户是谁？（具体角色，不是"所有人"）
- 解决什么痛点？（当前怎么做的？为什么不好？）
- 和现有功能怎么交互？（哪些模块会受影响？）
- 边界在哪？（明确不做什么，和做什么一样重要）

**优化/重构**——核心维度：
- 当前痛点能量化吗？（多慢？多少次出错？多少人受影响？）
- 改进目标可衡量吗？（"更快"不行，"P95 从 3s 降到 500ms"才行）
- 影响范围多大？（哪些下游依赖？）
- 风险在哪？（改错了最坏情况是什么？）

**配置/资产**——核心维度：
- 参照哪个现有配置？（找到最接近的同类，逐字段对比）
- 哪些字段必改？哪些可以沿用？
- 验证方式是什么？（怎么确认配对了？）
- 有没有联动配置？（改了这个，别的地方要不要跟着改？）

以上是常见类型。如果需求不属于这三种（比如集成第三方服务、数据迁移、安全修复等），根据需求的核心维度自行构造提问框架——关键是找到"做什么、为什么做、边界在哪、风险在哪"这四个维度的答案。

### Pushback 模式

用户回答不够具体时，追问：

**模糊需求 → 逼具体**
- 用户："我想让面板更好用"
- 不要："好的，有什么想法吗？"
- 应该："'更好用'可以指很多东西——是操作步骤太多？还是信息找不到？还是反馈不及时？你上次觉得不好用是在做什么操作的时候？"

**假想痛点 → 要证据**
- 用户："我觉得用户可能需要批量操作"
- 不要："批量操作是个好想法，怎么实现？"
- 应该："'可能需要'——有用户实际提过这个需求吗？还是从使用数据看到了什么模式？如果目前没人要求过，这个优先级可能需要重新评估。"

**单一方案 → 强制对比**
- 用户："我们用 WebSocket 来做实时通知"
- 不要："好的，WebSocket 怎么接入？"
- 应该："WebSocket 是一个选项。在决定之前，SSE 或者轮询在我们的场景下各有什么利弊？这值得在方案对比阶段做个正式对比。"

### 提问节奏

- 问完核心维度后，回顾一遍：有没有漏掉的维度？
- 如果用户的回答已经覆盖了某个问题，跳过它
- 通常 3-6 个问题足够，不要为了走流程而问不必要的问题

## 步骤 3：前提挑战

在提方案之前，挑战需求本身的前提。发散阶段的发现是这一步的证据基础——有发现就引用，不要重复搜索。

### ① 这是正确的问题吗？

换一种 framing，能否导向更简单或更有效的方案？

示例：用户说"给系统加个版本回滚功能" → 挑战："回滚是为了修复错误配置。如果编辑时就能预览效果、提交前做校验，需要回滚的场景会大幅减少。要不要把需求改成'提交前校验'？"

### ② 不做会怎样？

这是真痛点还是"有了更好"的假想需求？

- 如果不做，谁会受影响？影响频率和严重度？
- 有没有 workaround？workaround 的成本是什么？
- 如果答案是"其实也还好"——这个需求的优先级可能需要重新考虑

### ③ 现有代码已经部分解决了吗？

**快速路线**：用工具实际搜索。
**深潜/围猎路线**：直接引用发散阶段的发现（`findings.md` 或 `findings-final.md` 中的"已有资产"部分），不重复搜索。

如果找到了，评估"在已有基础上扩展" vs "从头做"的成本对比。

### ④ 产物怎么到用户手上？

如果需求的产物是**新工具、新脚本、新插件**等从无到有的东西：
- 用户怎么获取？依赖怎么装？
- Server 功能 → 热重载够还是需要全量重启？
- 客户端功能 → 怎么分发到用户？

如果产物是对现有系统的修改，交付路径已有——跳过此条。

---

将四个维度的判断汇总，向用户呈现：

```
前提检查：
① 问题定义：[确认正确 / 建议调整为 XXX]
② 不做的影响：[真痛点——理由 / 优先级存疑——理由]
③ 现有基础：[找到 XXX 可复用 / 需要从头做——理由]
④ 交付路径：[已有路径 / 需要设计——具体方案]
```

用户确认后，将判断结论暂存（写入 Spec 时填入 `## 关键决策` 区块）。如果前提挑战导致需求方向调整，回到步骤 2 补充提问。

## 步骤 4：方案对比

**强制生成 2-3 个方案。不可跳过。** 即使你觉得"明显只有一种做法"，也必须至少提出第二个方案。

### 方案结构

每个方案包含：

```
方案 A：[名称]
  概述：1-2 句话
  改动范围：涉及哪些文件/模块
  工作量：S / M / L
  优势：2-3 点
  风险：2-3 点
  复用：利用了哪些现有代码/模式
```

### 方案要求

- **至少一个"最小可行"方案**：最少文件、最小 diff、最快能用
- **至少一个"理想架构"方案**：长期最优、最干净
- **可选一个"创意/侧面"方案**：不同 framing、意想不到的路径

### 推荐

给出明确推荐和理由：`推荐方案 X，因为 [一句话理由]。如果 [条件]，方案 Y 会更好。`

用户选择并确认后，读取 `spec-write.md` 进入 Spec 写入阶段。

---

## Escape Hatch

如果用户表达不耐烦（"直接做吧"、"不用这么复杂"、"跳过问题"）：

**第一次**：
> "理解。让我问最关键的 2 个问题，然后直接进方案对比。"

**第二次**：
> "好的，快速过一遍前提检查（每条一句话判断），然后直接进方案对比。"

前提挑战可以压缩但不可跳过——它拦截的是"在错误的问题上做完美的分析"，这比多花 30 秒更贵。

**Spec 写入也不能跳。** 即使快进了前面的步骤，最终产出必须是一份写入文件的 Spec。
