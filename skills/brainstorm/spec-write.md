# 阶段 3：Spec & 交接

你已完成收敛阶段，用户确认了需求范围和选定方案。现在写入 Spec 文件。

---

## 步骤 1：写入 Spec

将确认的需求和方案写入 `$PROJECT_DIR/data/todo/{name}.md`。

文件名用小写 kebab-case，反映需求主题。

### Spec 文件结构

```markdown
# {需求标题}

**背景**：{一段话——触发原因、解决什么问题、成功标准}

**进度**：未开始 0/N

## Spec

### 用户故事
- 作为 {角色}，我想要 {功能}，以便 {价值}

### 约束清单
- {约束 1}
- {约束 2}

### 验收标准
- [ ] {标准 1——可判定的 yes/no}
- [ ] {标准 2}

### 验收场景（必填）

每条验收标准都必须有对应的验收场景。不可跳过此区块。

#### 功能验收

用户可见行为的端到端验证，采用「给定→当→则」格式：

- 给定 {前置条件}，当 {用户操作}，则 {预期结果}

### 架构决策
- {决策 1}：{选了什么方案，为什么}

## 关键决策

- {前提挑战中确认的决策}
- {方案对比中选择的方案及理由}

## 不在范围内

- {被排除的方案方向}：{为什么不做}

## 已有资产

- `{搜索到的可复用文件路径}`：{它已经做了什么，本次如何复用/改造}
```

**注意**：只写 Spec 部分、关键决策、不在范围内、已有资产。`## 子任务` 区块留给 /todo 来填充。

## 步骤 2：自检

写入后立即自检，发现问题直接修复：

1. **占位符扫描**：有没有"TBD"、"TODO"、"待定"、"后续补充"？→ 现在就确定
2. **内部矛盾**：约束清单和验收标准之间有没有冲突？架构决策和用户故事是否一致？
3. **范围检查**：这个 Spec 是否聚焦到一个可实现的单元？还是需要进一步拆分子项目？
4. **歧义检查**：有没有哪条需求可以被两种方式理解？→ 选一种，写明确
5. **验收场景完备性**：检查每条验收标准是否有对应的验收场景

## 步骤 3：可选独立审查

### 复杂度评估

统计 Spec 中 `### 验收标准` 区块的条目数。

- **验收标准 ≥5 条**（复杂 Spec）→ 主动推荐审查
- **验收标准 <5 条**（简单 Spec）→ 仅告知选项存在

当用户同意执行独立审查时，spawn 独立审查者对 Spec 做对抗审查。

## 步骤 4：衔接 /todo

Spec 确认后，提示用户：

> Spec 已就绪。现在用 /todo 把它拆解成可执行的子任务吗？

如果用户同意，告知用户输入 `/todo` 即可。

**不要自动调用 /todo**——让用户决定节奏。
