# 阶段 0：探查 & 校准

判断需求的复杂度，选择匹配的路线。

---

## 步骤 1：理解环境

在回应用户之前，快速建立项目认知：

1. 读 `CLAUDE.md`（如果存在）
2. `git log --oneline -10` 了解近期变更方向
3. 如果 `$PROJECT_DIR/data/todo/` 下有文件，扫描了解已有 plan 和 Spec

用 2-3 句话向用户确认你对项目现状的理解。

## 步骤 2：探查需求足迹

带着用户的需求描述，快速扫描代码库：

1. **涉及哪些模块？** 用 Grep/Glob 搜索与需求最相关的代码区域，列出涉及的目录和模块
2. **模块间有什么耦合？** 检查这些模块之间是否有 import、依赖、共享状态
3. **有没有现成的东西？** 是否已有部分实现、相似功能、可复用的组件

这一步是快速扫描（广度优先），不是深度分析——目标是画一张粗粒度的地图，判断需求的体量和耦合度。

## 步骤 3：校准路线

### 如果用户已指定路线

跳过校准，直接执行步骤 4。

### 如果用户未指定路线

基于步骤 2 的探查结果，用以下可观测信号判断：

**快速路线**（全部满足）：
- 涉及 ≤2 个模块或目录
- 模块间无跨模块耦合或共享状态
- 用户描述具体，无需澄清歧义
- 不涉及技术选型对比

**深潜路线**（满足任一）：
- 涉及 3-5 个模块或目录
- 存在跨模块交互或共享状态
- 需求描述有模糊之处需要澄清
- 涉及技术选型或方案对比

**围猎路线**（满足任一）：
- 涉及 >5 个模块或目录
- 模块间高度耦合（改一处影响多处）
- 需要迁移、大规模重构等"漏一个就失败"级别的完备性
- 需求涉及多个子系统的协调改动

模块数量是初筛信号，不是最终判断。如果模块数量指向某条路线但探查到的实际耦合度或改动量与该路线不匹配，以耦合度和改动量为准。

> **边界案例**：用户说"给用户列表加个搜索框"。涉及 1 个页面组件，描述具体——初看是快速路线。但如果探查发现用户列表有前后端分页、搜索需要后端 API 支持和数据库索引，实际涉及前端组件 + 后端 API + 数据库三个层面，应该走深潜。判断关键：模块数量按"需要改动的独立代码区域"计数，不按"用户提到的功能点"计数。

**不确定时选深潜**——深潜过程中发现复杂度超预期可以升级到围猎。围猎成本高，不轻易选择。

## 步骤 4：呈现校准结果

向用户呈现：

1. **需求理解**：用自己的话复述用户想做什么
2. **探查发现**：涉及哪些模块、耦合情况、现有基础（简要，不超过 5 条）
3. **推荐路线**：走哪条、为什么（1-2 句话）

等用户确认后，按路线分流：

- **快速** → 直接读取 `converge.md`
- **深潜** → 在 skill 目录下创建工作目录 `sessions/{YYYYMMDD-HHmmss}/`，然后读取 `diverge-deep.md`
- **围猎** → 在 skill 目录下创建工作目录 `sessions/{YYYYMMDD-HHmmss}/`，然后读取 `diverge-hunt.md`

### 升级机制

如果校准为快速，但在后续收敛阶段发现复杂度超出预期（出现了探查未发现的跨模块依赖、或多个独立子系统需要协调），向用户建议升级到深潜或围猎，回到本阶段重新分流。
