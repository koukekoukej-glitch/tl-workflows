# 核心方法论

> 两种工作模式共享的分析框架和评估标准。在分析/审计阶段按需加载。

---

## 正交性原则

上下文中只沉淀**模型通过自身工具无法在合理步数内发现**的信息。

| 值得沉淀（正交） | 不值得沉淀（冗余） | 有害（必须删除） |
|----------------|------------------|----------------|
| 术语映射（人类概念 → 代码标识符） | 目录结构（ls/Glob 一步获取） | 不完整的枚举列表（代表性节点、功能列表、职责划分） |
| 反知识（看起来对但已过期/废弃的数据源） | 文件命名规则（看几个例子可归纳） | 层级职责边界（"X 层负责 Y 功能"） |
| 隐式架构（跨数百文件的设计模式） | 函数签名/类名清单（Grep 直接定位） | 刚性行为指令（"第一个动作必须是..."） |
| 魔法数字语义（枚举值的业务含义） | 探索操作流程（模型自带探索策略） | |
| 跨层桥接（配表字段 → 代码类型，需多步推理） | 单文件内自解释的逻辑 | |

**有害信息的判断标准**：如果一条信息是模型能自行发现的完整集合的**子集**，给出这个子集比不给更糟——模型会把子集当穷举，不再搜索发现剩余部分。

**应用方式**：审计文档时，对每一行问两个问题：
1. "模型用 Grep + Read 能在 3 步内发现这个信息吗？"——能则标记为冗余候选
2. "这条信息是某个更大集合的子集吗？模型看到它会不会停止搜索？"——会则标记为有害候选

## 信息地图精确性

CLAUDE.md 中每个可加载文档条目必须精确回答两个问题：

1. **里面有什么信息？** 具体到信息类型，用编号列举（"①废弃数据源警告 ②管线架构 ③魔法数字含义"），不能是"XX 系统的架构和关键路径"
2. **什么时候需要？** 精确的触发条件（"遇到无法从代码推断的魔法数字时"），不能是"需要深入了解 XX 时"

**审计方法**：把自己当成 Agent——看到这个条目的描述，能否立刻判断"我现在需不需要加载这个文件"？如果判断有犹豫，描述不够精确。

## 四重检验

对每条拟修改/新增的上下文信息，逐条检验：

### 与模型能力正交

这条信息是模型通过自身工具无法在合理步数内发现的吗？如果能，不应该放在上下文中——它占据 token 却不产生价值，甚至可能与模型自身的探索策略冲突。

### 时机正确

这条信息所在的文件，是在 Agent 需要它的工作流阶段被加载的吗？

反面：定向查询工具的用法放在常驻文件中 → 诱导跳步；特定领域细节放在通用方法论中 → 无关 session 被迫加载。

### 位置正确

Agent 处理同类问题时，是否一定会加载这条信息所在的文件？如果可能绕过，信息就放错了位置。

### 长期有效

这条信息是稳定的吗？代码变更后它会不会变成误导？

**高过期风险**（慎重添加）：具体的表结构/字段名、针对特定 bug 的绕道指引、依赖当前目录结构的绝对路径。

**长期稳定**（优先选择）：架构层级关系、领域概念映射、方法论原则、不依赖实现细节的规则。

## 根因分类

### 内容层根因

| 根因 | 修复位置 | 修复形态 |
|------|---------|---------|
| 术语映射缺失 | 对应知识文档 | 新增映射行 |
| 路由关键词不足 | 路由/索引文件 | 补充关键词 |
| 信息描述模糊 | 信息地图条目 | 精确化描述 |
| 冗余信息干扰 | 对应知识文档 | 删除冗余内容 |
| 不完整枚举误导 | 对应知识文档 | 删除枚举，只保留模型自行发现的入口（目录路径、命名规则） |
| 知识文档缺失 | 新建文档 | 创建正交内容 |

### 架构层根因

| 根因 | 识别特征 | 修复形态 |
|------|---------|---------|
| 信息暴露时序错误 | Agent 在某步骤使用了不应看到的信息 | 移到正确时机加载的文件 |
| 文件职责边界不清 | 一个文件同时服务多个步骤 | 按工作流步骤拆分 |
| 工作流路由缺陷 | Agent 无法判断走哪条路径 | 明确路径分类和判断依据 |
| 路由授权过宽 | Agent 可以"合理"跳过整个流程 | 收紧判断条件或改为分类路由 |

### 补丁 vs 重构

- "缺了一条信息" → **补丁**
- "信息在错误的位置/时机" → **重构**
- 补丁后 Agent 仍大概率走相同错误路径 → 说明需要**重构**

---

## 修改守则

**修复力度匹配根因深度**：信息缺失 → 最小修改直接补；信息位置错误 → 移动信息；结构缺陷 → 结构性重组。不要用补丁掩盖结构问题，也不要用重构解决补丁就能修的问题。

**反模式优先**："不要这样做"比"应该这样做"更有效。但反模式必须放在 Agent 即将做对应决策的位置。

**保持简洁**：每增加一行，同时审视有没有可以移除的冗余。

**反过拟合**：
- **事实补充**（术语映射、模块入口、数据关系）：单 session 证据即可，这是客观信息
- **方法论/规则变更**（调查策略、工作流规则）：需要 ≥2 个 session 支持，或能论证该问题必然影响同类 session

## 常见失败模式

| 模式 | 信号 | 典型根因 |
|------|------|---------|
| 路由迷失 | 前 N 步在不同模块间跳转 | 路由入口缺失或关键词不足 |
| 上下文失效 | Agent 完全跳过所有文档直接行动 | 路由条件过宽，Agent 判断不需要文档 |
| 信息暴露过早 | Agent 在理解阶段就发起调查操作 | 调查工具/信息放在了常驻层 |
| 过度调查 | 调用数远超同类问题所需 | 调查策略引导不够聚焦 |
| 盲搜爆炸 | 多轮全局搜索不同关键词 | 跳过路由文档直接搜代码 |
| 术语错配 | Agent 回答的领域和用户问的不一致 | 术语映射缺失或歧义 |
| 冗余噪音 | Agent 加载了大量文档但未使用 | 文档信噪比低，正交信息不足 |
| 枚举锚定 | Agent 从文档列表中选答案而不搜索代码确认 | 文档给了不完整的枚举（代表性节点、功能列表），Agent 把列表当穷举 |
| 职责误导 | Agent 只在某一层搜索，跳过了正确的层 | 文档给技术层划了职责边界（"X 层管 Y"），模型不在其他层搜索 Y |
| 行为漂移 | Agent 绕道或做出不合理回避 | 过期的反模式仍在上下文中 |
