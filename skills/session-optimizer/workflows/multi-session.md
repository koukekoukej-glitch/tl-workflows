# 多 Session 深度分析工作流

> 前置条件：已完成 SKILL.md 中的 Phase 1（理解 Agent 身份）。

本工作流有三种子模式，根据用户意图选择：

| 用户意图 | 子模式 | 起始步骤 |
|---------|--------|---------|
| "对比 Conv X 和 Conv Y" | **A/B 对比** | Step 1 |
| "系统性审计/优化上下文工程" | **系统审计** | Step 3 |
| "批量验证/回测" | **批量回测** | Step 5 |

子模式可以串联——A/B 对比中发现系统性问题可升级为系统审计，系统审计完成后可规划批量回测。

---

## A/B 对比分析（Step 1-2）

### Step 1：控制变量分析

1. 加载两个 session 的报告（export + metrics）
2. 识别**控制变量**：两个 session 的用户输入是否相同/相似？上下文版本差异是什么？
3. 对两个 session 分别做第一视角还原（方法同 `workflows/single-session.md` Step 2）
   - 逐一还原每个 Agent 在每个决策点看到了什么、选择了什么
   - **不要跳过第一视角还原直接给结论**——这是核心方法，没有捷径

### Step 2：因果归因

对比两个 Agent 的行为差异，追问因果：

1. **行为差异清单**：Agent A 做了什么 Agent B 没做的？反之呢？
2. **上下文差异→行为差异的因果链**：哪条上下文变化导致了哪个行为差异？
3. **效果评估**：
   - 效率：工具调用数、费用、耗时
   - 完整性：收集的信息是否覆盖了问题的所有方面
   - 准确性：最终结论是否正确
4. **关键判断**：行为差异是上下文工程有意引导的改善，还是意外的副作用？
   - 如果 Agent 跳过了某个步骤——是"有依据的正确跳过"还是"上下文失效导致碰巧跳过"？

> A/B 对比的价值在于控制变量。如果发现上下文变化导致了**非预期的行为变化**，这是上下文工程的结构性信号，考虑升级为系统审计。

---

## 系统审计（Step 3-4）

### Step 3：原则推导与文档审计

加载 `references/core-methodology.md`，对 Agent 的整个上下文体系做审计：

**3a. 信息地图审计**

对 CLAUDE.md 中的每个可加载文档条目，检查：
- **内容描述是否精确？** 必须具体到信息类型（"①废弃数据源 ②管线架构 ③魔法数字含义"），不能是"XX 系统的架构和关键路径"
- **触发条件是否精确？** 必须是可判断的条件（"遇到无法从代码推断的魔法数字时"），不能是"需要深入了解时"

**3b. 正交性审计**

对每个深层知识文档，逐行检查：
- 这行信息是模型通过 Grep/Read/Glob/ls 在合理步数内能自行发现的吗？→ 能则标记为冗余
- 估算文档的**信噪比**：正交信息行数 / 总行数

**3c. 工作流审计**

检查 CLAUDE.md 中的工作流路由：
- 路径分类是否覆盖了用户输入的主要类型？
- 每条路径的首步动作是否明确？
- 边界情况（如"同时给了代码标识符和术语"）是否有处理规则？
- Agent 是否有"合理跳过整个流程"的空间？如果有，这个判断依据是否充分？

### Step 4：重构计划

基于审计发现，制定重构计划：

**4a. 变更清单**

| # | 文件 | 改动类型 | 变更摘要 | 四重检验 | 预期效果 |
|---|------|---------|---------|---------|---------|
| 1 | ... | 精简/重构/新建 | ... | 正交✓ 时机✓ 位置✓ 长期✓ | ... |

**4b. 验证先行**

对涉及事实性内容的文档（如深层知识），**先派 Agent 到代码库验证准确性，再重写**：
- 文档中声称的每条知识，到实际代码中确认是否仍然准确
- 标记"已验证 / 已过期 / 需更新"
- 扫描是否有文档中遗漏的正交信息

**4c. 执行**

- 等用户确认计划后执行
- 重写文档时同步更新交叉引用（其他文档中对此文档的引用路径和描述）
- 旧文件如果被替换（如更名），删除旧文件避免歧义

**4d. 写入重构记录**

写入 `data/optimization_log/` 保存完整的重构计划和执行记录，作为后续回测的基线。

## 批量回测（Step 5-6）

### Step 5：案例选择

从历史会话中筛选回测案例，选择标准：

- 涉及代码探索/分析（非纯查询等简单任务）
- 覆盖不同**路径类型**（CLAUDE.md 中定义的各条工作流路径）
- 覆盖不同**代码模块**和**问题类型**
- 优先选择曾经出问题或效率低的会话

产出**覆盖矩阵**，确保案例集在各维度上有足够覆盖：

| 维度 | 覆盖情况 |
|------|---------|
| 路径类型 | 直接探索(#N) / 路由探索(#N) / 深度调查(#N) / ... |
| 代码模块 | 前端(#N) / 后端(#N) / 数据层(#N) / 跨模块(#N) |
| 问题类型 | bug 调查 / 机制解释 / 是否生效 / 需求分析 / ... |

### Step 6：执行回测与对比

对每个案例：
1. 提取原始用户输入
2. 在新上下文下重放会话（通过项目的 replay 工具或 `/replay-session` 命令）
3. 对比原始 vs replay 的关键指标（工具数、费用、耗时、纠错轮次）
4. 用第一视角还原分析行为差异
5. 判断：效率提升？全面性提升？准确性提升？有无退化？

汇总所有案例的对比结果，形成整体验证报告。
