description: 记录或更新待办项。审视当前会话内容，将后续计划整理为 to-do 文档
---

审视当前上下文窗口中的所有内容（对话、决策、技术细节、已完成/未完成的工作），将后续计划整理为结构化的 plan 文档，存入 `data/todo/`。

**核心目标**：生成的文档应该让 `/vibe run` 仅凭此文档就能自动化执行所有子任务。

## 判断逻辑

1. **检查现有 plan**：先用 `ls $PROJECT_DIR/data/todo/` 查看已有文档列表
2. **判断模式**：
   - 如果当前会话讨论的主题与某个已有 plan 文档匹配 → **更新模式**
   - 如果是新任务 → **新建模式**
3. 如果无法确定，询问用户

## 新建模式

在 `$PROJECT_DIR/data/todo/` 下创建新的 markdown 文件：
- 文件名用小写 kebab-case，反映任务主题（如 `feature-auto-update.md`）
- 使用下方的文档模板

### 步骤零：Scope 守卫

任务拆解前，先回答三个问题。任何一条触发，暂停并向用户确认：

1. **已有资产复用**：先检查 plan 文件的 `## 已有资产` 区块——如果非空（说明 /brainstorm 已完成资产扫描），跳过此项检查并输出"brainstorm 已完成资产扫描，跳过重复检查"。如果为空或不存在，当前代码库中有没有已经部分或完全解决了 Spec 中某个子问题的代码？用 Grep/Glob 搜索确认，列出可复用的模块/函数及其路径
2. **最小变更集**：要达到 Spec 的验收标准，最少需要改动哪些文件？如果预估 > 8 个文件或新增 > 2 个模块/类，挑战是否有更简单的路径
3. **可拆分性**：Spec 是否覆盖了多个独立子系统？如果是，建议拆成多个 plan，每个独立可验证

将第 1 条的发现填入文档模板的 `## 已有资产` 区块。

### 步骤一：Spec 提取

从当前对话上下文中识别并提取结构化 Spec 信息，填充到文档模板的 `## Spec` 区块中：
- **用户故事**：从对话中提炼"谁、要什么、为什么"
- **约束清单**：用户明确提出的限制条件（技术选型、兼容性、性能要求等）
- **验收标准**：用 checkbox 列出可判定的验收条件
- **架构决策**：对话中确定的技术方案及其理由

如果对话中某类信息不明确，留空或标注"待确认"，**不要捏造**。

### 步骤二：任务拆解

按「子任务拆解原则」将工作拆解为原子任务，填入 `## 子任务` 区块。

### 步骤三：质量自检

Plan 写完后，**自动**逐任务运行以下自检清单：

1. **粒度合理**：单任务是否 ≤ 15 分钟估算工作量 / ≤ 200 行预估变更？
2. **退出标准可判定**：退出标准是否是明确的 yes/no？（"实现 XX 功能"不行，"XX 测试通过 + YY 组件可渲染"才行）
3. **验证命令完整**：是否有 `**验证命令**` 字段？命令是否是完整可执行的 shell 命令？（`npx vitest run path/to/test.ts` 行，`运行相关测试` 不行）
4. **自包含**：新 session 只读任务描述 + plan 头部信息能否直接执行？输入上下文是否列出了所有需要读的文件？
5. **Spec 覆盖完备**：`## Spec > ### 验收标准` 中的每一条，是否都能指向至少一个子任务？列出无任务覆盖的验收标准
6. **跨任务命名一致**：扫描所有子任务描述中出现的函数名、变量名、文件路径——同一个实体在不同任务中的名称是否一致？（如 T3 写 `processOrder` 但 T7 写 `handleOrder`）
7. **关键路径有测试覆盖**：涉及认证、安全、数据持久化、外部 API 调用的任务，验证命令中是否指向覆盖该路径的测试文件？如果不存在对应测试，在任务中加一个子步骤"补充测试"
8. **退出标准边界覆盖**：对每条退出标准，逐条检查：
   - 涉及数据传递的标准（A 模块输出 → B 模块消费），是否覆盖了**首次/空值/默认值**路径？
   - 涉及多组件协作的标准（命令模板 → 面板模板 → 脚本），验证命令是否检测**跨组件接口一致性**（不只是各自编译通过）？
   - 验证命令是否只检查"存在性"（`grep` 关键词）而非"正确性"（实际行为）？如果是，要么改写为行为验证命令，要么在退出标准旁标注 `[WEAK]` 并补充说明需要什么级别的代码审查
9. **证伪检查**：对每条退出标准，反问"此标准通过的同时，什么情况仍然代表失败？"如果能找到这样的情况，将其转化为**反面约束**追加到退出标准中，并补充对应的验证命令。不要求穷举——一轮对抗性思考，捕捉最显著的遗漏即可
10. **E2E 验收覆盖**：检查 `## Spec` 中是否存在 `### 验收场景` 区块且内容非空。如果验收场景非空，则子任务列表**末尾**必须有一个专门的 E2E 验收测试任务，且该任务的验证命令包含 `npx playwright test`（或等效的 E2E 测试命令）。如果 Spec 没有 `### 验收场景` 区块或该区块为空，此检查自动跳过——不强制所有 plan 都有 E2E 任务
11. **跨模块集成测试覆盖**：扫描所有子任务的文件地图和导出接口——是否存在 ≥2 个任务产出不同模块且模块间有调用关系（A export → B import）？如果是，检查是否存在一个独立的集成测试任务，且该任务的 mock 边界仅在外部依赖层、内部模块真实串联。缺失则新建

自检完成后，在输出给用户的内容中标注不达标的任务。格式：

```
⚠️ 质量自检发现 {N} 个待改进项：
- T5「实现搜索功能」：退出标准不够具体，建议改为"精确搜索+模糊搜索均可用，搜索结果高亮"
- T8「重构数据层」：缺少验证命令，建议加 `npx tsc --noEmit && npx vitest run server/src/data/`
```

如果所有任务均通过自检，输出 `✅ 质量自检通过，所有任务达标`。

自检发现问题时，**先自动修正能修正的项**（如补充验证命令、细化退出标准），修正后仍有无法自动解决的问题再标注给用户确认。

## 更新模式

读取已有的 plan 文档，根据当前会话进展：
- 标记已完成的子任务（状态改为 `✅ 已完成`，填写「产出」和「传递信息」）
- 追加新发现的子任务
- 更新「关键决策」（新增或修正）
- 更新「进度」计数
- 在文末追加更新记录
- **如果所有子任务均已完成 → 直接删除该 plan 文件**（不保留存档，保持目录整洁）

## 子任务拆解原则

- **粒度**：每个子任务应该能在一个短会话内完成（约 15-30 轮交互），预估 ≤ 15 分钟工作量 / ≤ 200 行变更。如果一个子任务需要改 10+ 个文件或涉及多个模块，应进一步拆分
- **自包含**：每个子任务的「输入上下文」必须写清所有前置信息。假设执行者对之前的讨论一无所知，只有这个 plan 文件
- **可验证**：退出标准必须是客观可验证的 yes/no 判定（"XX 测试通过 + YY 组件可渲染"），不能是模糊的主观判断（"实现 XX 功能"不行）
- **验证命令必填**：每个任务必须有 `**验证命令**` 字段，且命令必须是可直接执行的完整 shell 命令（如 `npx vitest run server/src/agent/tools/__tests__/foo.test.ts`），不能写模糊描述（如"运行相关测试"）。至少包含一条 build、typecheck 或测试命令
- **依赖最小化**：尽量让子任务独立。如果某个子任务同时依赖多个前置，考虑能否重新划分让依赖链更简单
- **文件地图前置**：在拆任务之前，先列出本次 plan 会创建/修改/测试的所有文件路径，作为 `## 文件地图` 放在子任务区块之前。这能让后续任务自动对齐，避免跨任务的文件冲突遗漏
- **退出标准的验证强度应匹配行为复杂度**：编译通过（`tsc --noEmit`）只证明类型安全，不证明行为正确。当任务涉及状态机、条件分支、时序逻辑等有状态行为时，退出标准必须包含行为级验证（测试用例或可执行的断言命令），而非仅依赖编译检查。验证手段的强度要和改动的复杂度对称
- **验证命令始终使用相对路径，由调度器在派发时注入工作目录上下文**：不在验证命令中硬编码任何绝对路径。正确写法：`grep -c "keyword" path/to/file.md`（相对路径），调度器在派发步骤自动注入 `cd {worktree_path} &&` 前缀。硬编码绝对路径会击穿 worktree 隔离——子 Agent 为了让验证命令通过，会操作主仓库而非 worktree，导致 commit 直接污染 main
- **跨任务的接口变更必须在消费方 spec 中显式声明**：当下游任务需要上游任务导出函数、修改类型签名、或改变文件结构时，必须在下游任务的「输入上下文」或「范围」中写明这一前置条件（如"需要 T1 将 `makeXxx` 从文件内部函数改为 export"）。不依赖子 Agent 自行发现并修改上游输出——这会导致合并冲突和不可预测的副作用
- **跨模块调用链必须有集成测试任务**：当 plan 中 ≥2 个任务分别产出不同模块，且这些模块之间存在调用关系（A export → B import）时，最后一个模块任务之后必须插入一个独立的集成测试任务。该任务的 mock 边界仅在外部依赖层（SDK、网络、数据库），内部模块之间真实串联。目的：单元测试各自 mock 邻居，接口假设可能不一致——集成测试是唯一能捕捉 mock 缝隙的手段

### 禁止的写法（No Placeholders）

以下写法是 plan 失败——执行者是全新 Agent 会话，对项目一无所知，任何模糊描述都等于猜：

| 禁止 | 为什么 | 应该写 |
|------|--------|--------|
| "TBD"、"TODO"、"待定"、"后续补充" | 执行者不知道该填什么 | 现在就确定，或标注为独立子任务 |
| "添加适当的错误处理" | 什么错误？怎么处理？ | "对 API 返回的 4xx 状态码抛出 AppError，5xx 重试 3 次" |
| "运行相关测试" | 哪个文件？哪个命令？ | `npx vitest run server/src/xxx.test.ts` |
| "参照 T1 的做法" | 执行者可能不按顺序做，或 T1 还没做 | 重复写出完整代码/步骤 |
| "实现 XX 功能" 作为退出标准 | 无法判定 yes/no | "XX 接口返回正确的 JSON + YY 测试通过" |
| "修改相关配置" | 哪个文件？改什么字段？ | "在 config.ts 中将 MAX_RETRY 从 3 改为 5" |

<RATIONALIZATION-PREVENTION>
写 plan 时你会想跳过细节的理由，以及为什么不能跳：

| 你会想的 | 现实 |
|----------|------|
| "验证命令太细了，执行者会自己判断" | 执行者是全新 session，对项目一无所知，模糊命令 = 猜 |
| "这个任务不需要测试" | 没有验证命令的任务无法判定是否完成，/vibe run 无法自动验证 |
| "退出标准写'功能正常'就够了" | "正常"没有客观判定标准，不同 Agent 理解不同 |
| "参考另一个任务就行" | 执行者可能不按顺序做，或另一个任务的上下文已丢失 |
| "太细了反而限制执行者" | 细节不限制——它提供信息。缺信息才是真正的限制 |
| "这个 plan 很简单，不需要 Scope 检查" | 简单的 plan 检查耗时 10 秒，复杂的 plan 不检查可能浪费整个执行周期 |
| "验证命令 `grep` 关键词存在就够了" | 存在性 ≠ 正确性。`grep "default_workspace"` 只证明字符串出现过，不证明它被正确传递和使用。这不是验证，是自欺 |
</RATIONALIZATION-PREVENTION>

## 格式约束（scan-todo.js 解析器依赖）

以下格式是 `/vibe run` 解析器（`$PROJECT_DIR/scripts/scan-todo.js`）能识别的**唯一格式**，生成和更新时必须严格遵守：

1. **进度行**（必须存在，文件顶部，`## 关键决策` 之前）：
   ```
   **进度**：未开始 0/Y
   **进度**：进行中 X/Y
   **进度**：已完成
   ```

2. **子任务标题行**（二选一，不可混用其他格式）：
   - 标题格式：`### T{数字}: {任务名} {emoji} {状态}`
     ```
     ### T1: 组件级架构图 ⬚ 待开始
     ### T2: 数据流走查 🔄 进行中
     ### T3: 边界与接口 ✅ 已完成
     ```
   - 表格格式：`| {阿拉伯数字} | 任务名 | ... | {emoji或状态文字} | ... |`
     ```
     | 1 | 用 /security-review 做全面审计 | High | ⬚ | ... |
     ```

3. **禁止的格式**（扫描器无法识别）：
   - `### 子任务 1.1:` — 不以 `T` 开头
   - `### P1a-Step1:` — 不以 `T` + 数字开头
   - `#### 阶段 0:` — 四级标题
   - `| 一 | 任务名 |` — 中文数字
   - `Phase 1: ... ✅` — 行内 Phase 标记

4. **分组**：如果子任务有逻辑分组（阶段/Phase），用 `## {分组名}` 二级标题做 section 标记，子任务本身仍用 `### T{N}:` 连续编号。

## 写入规则

- 文件路径必须使用项目绝对路径：`$PROJECT_DIR/data/todo/{name}.md`
- 涉及文件要标注具体路径
- 技术细节部分写清上下文——假设读者对当前会话一无所知
- 每次更新在「更新记录」表格追加一行
