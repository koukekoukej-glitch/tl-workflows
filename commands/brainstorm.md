# Brainstorm：需求收敛器

把模糊想法变成完整 Spec 文件，自动衔接 /todo 做任务拆解。

<HARD-GATE>
在 Spec 文件写入且用户确认之前，不允许：
- 写任何代码
- 创建任何实现文件
- 调用 /todo、/vibe 或任何实现类命令
- 给出具体的代码实现建议

这适用于所有需求，无论看起来多简单。
</HARD-GATE>

## Anti-Pattern："这个太简单了，不需要走流程"

每个需求都走这个流程。一个配置改动、一个小工具、一个"只是加个字段"——全部。"简单"需求恰恰是未经检验的假设造成最多返工的地方。Spec 可以短（几句话），但必须经过 Premise Challenge 和用户确认。

---

## Phase 0: Context Gathering

理解项目当前状态和用户要改动的区域。

1. 读 `CLAUDE.md`（如果存在）
2. `git log --oneline -10` 了解近期变更方向
3. 用 Grep/Glob 扫描与用户需求最相关的代码区域
4. 如果 `$PROJECT_DIR/data/todo/` 下有相关的 plan 文件，读取了解背景

产出：用 2-3 句话向用户确认你对项目现状和改动区域的理解。

---

## Phase 1: Scope 预判

在问细节之前，先判断这个需求的规模。

**判断标准**：这是一件事还是多件独立的事？

- 如果用户说"做一个面板系统+数据绑定+权限控制"→ 这是多件事，应该先拆成子项目
- 如果用户说"给编辑器加个搜索功能"→ 这是一件事，直接进 Phase 2

**大需求的处理**：
1. 列出识别到的独立子项目
2. 建议处理顺序（依赖关系、优先级）
3. 与用户确认后，对第一个子项目进入 Phase 2
4. 每个子项目走独立的 Brainstorm → Spec → /todo 周期

---

## Phase 2: Questioning

**一次只问一个问题。** 等用户回答后再问下一个。不要在一条消息里堆多个问题。

**尽量用多选题。** 能给选项就给选项——选比写快，而且 Agent 基于代码库上下文生成的选项往往能覆盖用户没想到的方向。开放式问题留给真正需要自由表达的地方（如"你想解决什么痛点"）。

### 需求类型分流

先判断需求类型，选择对应的提问框架：

**新功能**——核心维度：
- 用户是谁？（具体角色，不是"所有人"）
- 解决什么痛点？（当前怎么做的？为什么不好？）
- 和现有功能怎么交互？（哪些模块会受影响？）
- 边界在哪？（明确不做什么，和做什么一样重要）

**优化/重构**——核心维度：
- 当前痛点能量化吗？（多慢？多少次出错？多少人受影响？）
- 改进目标可衡量吗？（"更快"不行，"P95 从 3s 降到 500ms"才行）
- 影响范围多大？（哪些下游依赖？）
- 风险在哪？（改错了最坏情况是什么？）

**配置/资产**——核心维度：
- 参照哪个现有配置？（找到最接近的同类，逐字段对比）
- 哪些字段必改？哪些可以沿用？
- 验证方式是什么？（怎么确认配对了？）
- 有没有联动配置？（改了这个，别的地方要不要跟着改？）

### Pushback Patterns

当用户的回答不够具体时，追问。以下是三种常见情况和示范：

**模式 1：模糊需求 → 逼具体**
- 用户："我想让面板更好用"
- 不要说："好的，有什么想法吗？"
- 应该说："'更好用'可以指很多东西——是操作步骤太多？还是信息找不到？还是反馈不及时？你上次觉得不好用是在做什么操作的时候？"

**模式 2：假想痛点 → 要证据**
- 用户："我觉得用户可能需要批量操作"
- 不要说："批量操作是个好想法，怎么实现？"
- 应该说："'可能需要'——有用户实际提过这个需求吗？还是从使用数据看到了什么模式？如果目前没人要求过，这个优先级可能需要重新评估。"

**模式 3：单一方案 → 强制对比**
- 用户："我们用 WebSocket 来做实时通知"
- 不要说："好的，WebSocket 怎么接入？"
- 应该说："WebSocket 是一个选项。在决定之前，SSE（Server-Sent Events）或者轮询在我们的场景下各有什么利弊？这个决策值得在 Phase 4 做个正式对比。"

### 提问节奏

- 问完核心维度后，回顾一遍：有没有漏掉的维度？
- 如果用户的回答已经覆盖了某个问题，跳过它
- 通常 3-6 个问题足够，不要为了走流程而问不必要的问题

---

## Phase 2.5: Landscape Search（可选）

**仅在以下情况触发**：
- 用户主动要求"先查查别人怎么做的"
- 需求涉及技术选型（选框架、选方案）且你不确定最新生态

**搜索原则**：
- 使用通用术语搜索，不暴露具体项目细节
- 搜索关键词示例："[技术方向] best practices {current year}"、"[问题类型] common approaches"
- 读取前 2-3 个结果，提取与当前需求相关的信息

**不触发时直接跳到 Phase 3。**

---

## Phase 3: Premise Challenge

在提方案之前，挑战需求本身的前提。这是防止"在错误的问题上做完美的分析"的关键环节。

逐一检查以下维度，每个都要给出明确判断（不是走形式）：

### ① 这是正确的问题吗？

换一种 framing，能否导向更简单或更有效的方案？

示例：用户说"给系统加个版本回滚功能" → 挑战："回滚是为了修复错误。如果编辑时就能预览效果、提交前做校验，需要回滚的场景会大幅减少。要不要把需求改成'提交前校验'？"

### ② 不做会怎样？

这是真痛点还是"有了更好"的假想需求？

- 如果不做，谁会受影响？影响频率和严重度？
- 有没有 workaround？workaround 的成本是什么？
- 如果答案是"其实也还好"——这个需求的优先级可能需要重新考虑

### ③ 现有代码已经部分解决了吗？

**用工具实际搜索，不靠猜。**

- 用 Grep/Glob 搜索相关的函数、模块、工具
- 检查是否有已有的部分实现、相似功能、可复用的组件
- 如果找到了，评估"在已有基础上扩展" vs "从头做"的成本对比

### ④ 产物怎么到用户手上？

如果需求的产物是**新工具、新脚本、新插件**等从无到有的东西，在需求阶段就想清楚交付路径：

- 脚本/工具 → 用户怎么获取？依赖怎么装？
- Server 功能 → 热重载够还是需要全量重启？
- 客户端功能 → 怎么分发到用户？

**如果产物是对现有系统的修改，交付路径已有——跳过此条。**

---

将四个维度的判断汇总，向用户呈现：

```
前提检查：
① 问题定义：[确认正确 / 建议调整为 XXX]
② 不做的影响：[真痛点——理由 / 优先级存疑——理由]
③ 现有基础：[找到 XXX 可复用 / 需要从头做——理由]
④ 交付路径：[已有路径 / 需要设计——具体方案]
```

用户确认后，将四个维度的判断结论写入 Spec 文件的 `## 关键决策` 区块（如果文件尚不存在，此时创建）。特别保留：
- ② "不做会怎样"的判断——这是需求优先级的依据
- ③ 搜索到的可复用代码——后续填入 `## 已有资产`
- ④ 交付路径的方案——后续作为架构约束

进入 Phase 4。如果 Premise Challenge 导致需求方向调整，回到 Phase 2 补充提问。

---

## Phase 4: Alternatives

**强制生成 2-3 个方案。这不是可选的。**

即使你觉得"明显只有一种做法"，也必须至少提出第二个方案。单一方案 = 确认偏误。

### 方案结构

每个方案包含：

```
方案 A：[名称]
  概述：1-2 句话
  改动范围：涉及哪些文件/模块
  工作量：S / M / L
  优势：2-3 点
  风险：2-3 点
  复用：利用了哪些现有代码/模式
```

### 方案要求

- **至少一个"最小可行"方案**：最少文件、最小 diff、最快能用
- **至少一个"理想架构"方案**：长期最优、最干净
- **可选一个"创意/侧面"方案**：不同 framing、意想不到的路径

### 推荐

给出明确推荐和理由：`推荐方案 X，因为 [一句话理由]。如果 [条件]，方案 Y 会更好。`

用户选择并确认后进入 Phase 5。

---

## Phase 5: Spec Write + Self-Review

### 5a. 写入 Spec

将确认的需求和方案写入 `$PROJECT_DIR/data/todo/{name}.md`。

文件名用小写 kebab-case，反映需求主题。

写入的内容结构（与 /todo 模板对齐）：

```markdown
# {需求标题}

**背景**：{一段话——触发原因、解决什么问题、成功标准}

**进度**：未开始 0/N

## Spec

### 用户故事
- 作为 {角色}，我想要 {功能}，以便 {价值}

### 约束清单
- {约束 1}
- {约束 2}

### 验收标准
- [ ] {标准 1——可判定的 yes/no}
- [ ] {标准 2}

### 验收场景（必填）

每条验收标准都必须有对应的验收场景。不可跳过此区块。

#### 功能验收

用户可见行为的端到端验证，采用「给定→当→则」格式：

- 给定 {前置条件}，当 {用户操作}，则 {预期结果}

### 架构决策
- {决策 1}：{选了什么方案，为什么}

## 关键决策

- {Premise Challenge 中确认的决策}
- {Phase 4 中选择的方案及理由}

## 不在范围内

- {Phase 4 中被排除的方案方向}：{为什么不做}

## 已有资产

- `{Phase 3 ③ 搜索到的可复用文件路径}`：{它已经做了什么，本次 plan 如何复用/改造}
```

**注意**：
- 只写 Spec 部分、关键决策、不在范围内、已有资产。`## 子任务` 区块留给 /todo 来填充。

### 5b. Self-Review（4 步自检）

写入后立即自检，发现问题直接修复：

1. **占位符扫描**：有没有"TBD"、"TODO"、"待定"、"后续补充"？→ 现在就确定
2. **内部矛盾**：约束清单和验收标准之间有没有冲突？架构决策和用户故事是否一致？
3. **范围检查**：这个 Spec 是否聚焦到一个可实现的单元？还是需要进一步拆分子项目？
4. **歧义检查**：有没有哪条需求可以被两种方式理解？→ 选一种，写明确
5. **验收场景完备性**：检查每条验收标准是否有对应的验收场景。

### 5c. 独立审查（可选对抗审查）

当用户同意执行独立审查时，调用独立审查者进行对抗审查。

### 5d. 复杂度评估 + 用户确认

**复杂度评估**：统计 Spec 中 `### 验收标准` 区块的条目数。

- **验收标准 ≥5 条**（复杂 Spec）→ 主动推荐审查
- **验收标准 <5 条**（简单 Spec）→ 仅告知选项存在

---

## Phase 6: 衔接 /todo

Spec 确认后，提示用户：

> Spec 已就绪。现在用 /todo 把它拆解成可执行的子任务吗？

如果用户同意，告知用户输入 `/todo` 即可。

**不要自动调用 /todo**——让用户决定节奏。

---

## Escape Hatch

如果用户表达不耐烦（"直接做吧"、"不用这么复杂"、"跳过问题"）：

**第一次**：
> "理解。让我问最关键的 2 个问题，然后直接进方案对比。"

**第二次**：
> "好的，直接进方案对比。"

**但 Phase 5（Spec 写入）不能跳。** 即使快进了前面的步骤，最终产出必须是一份写入文件的 Spec。

<RATIONALIZATION-PREVENTION>
你会想跳过步骤的理由，以及为什么不能跳：

| 你会想的 | 现实 |
|----------|------|
| "用户已经想清楚了，不需要 Premise Challenge" | 用户认为想清楚了 ≠ 真的想清楚了。未经挑战的假设是返工的头号来源 |
| "只有一种实现方式，没法对比" | 几乎不存在"只有一种方式"。至少可以对比"最小实现" vs "完整实现"的范围取舍 |
| "这个需求太简单，写 Spec 浪费时间" | 简单需求的 Spec 只需要几句话。写 Spec 花 2 分钟，漏掉需求返工花 2 小时 |
| "Premise Challenge 会让用户觉得我在质疑他" | 你不是在质疑用户的判断，你是在帮他检查盲点。好的产品经理都这么做 |
| "直接帮用户写代码更高效" | 写对的代码比写快的代码更高效。Spec 就是"对"的定义 |
</RATIONALIZATION-PREVENTION>
