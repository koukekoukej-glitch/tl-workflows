从 `/vibe run` 的执行报告中做方法论审计，提炼结构性改进并沉淀到 `/todo` command 中。

**用户参数**：`$ARGUMENTS` — 可选的 plan 名称（如 `interactive-panel-system`）

## 核心原则

### 补丁 vs 方法论

模型能力会持续增强。review 的价值不在于修补今天遇到的具体问题，而在于沉淀**不管模型多强都需要遵循的结构性纪律**。

| 补丁（不要） | 方法论（要） |
|-------------|-------------|
| "百分比阈值必须有采样验证" | "退出标准基于可观测行为，不预测实现细节" |
| "新建文件 finish 前检查 untracked" | "调度器在架构边界处需要显式协调步骤" |
| "如果遇到 X 就做 Y" | "始终/永远/不要 ..." |

**准入标准**：
- 能用 **always/never** 表述 → 方法论，可沉淀
- 只能用 **if-then** 表述（"如果遇到 X 就做 Y"）→ 补丁，不沉淀
- 模型下一代大概率自然改善的 → 不沉淀（如"子 Agent 忘了读 plan"、"提交信息写得不好"）

### 分析思维模式

不是问"哪个任务出了什么问题"，而是问：
1. **这次执行暴露了哪些 plan 定义方式的系统性短板？** — 退出标准怎么写的、任务边界怎么划的、依赖怎么声明的
2. **调度器/流水线的执行纪律有没有结构性缺陷？** — 不是某次 finish 失败，而是 finish 流程在哪类场景下会系统性地出问题
3. **哪些"成功"实际上是侥幸？** — 全部 PASS 不代表没问题，可能是退出标准太弱、验证命令没有真正验证声称的行为

## 执行流程

### Step 1：定位执行报告

```bash
ls $PROJECT_DIR/data/auto-run-logs/*-summary.md 2>/dev/null
```

- 如果 `$ARGUMENTS` 非空 → 在 `data/auto-run-logs/` 中查找匹配 `{$ARGUMENTS}-*-summary.md` 的文件，取最新的一个
- 如果 `$ARGUMENTS` 为空 → 列出所有 summary 文件，让用户选择
- 没有找到 → 告诉用户"未找到执行报告，请先运行 `/vibe run <plan-name>`"，结束

### Step 2：读取并分析

读取 summary 文件全文。同时查看 `data/auto-run-logs/` 中该 plan 的其他日志文件（`*-result.md`、`*-eval-report.md`），获取任务详细信息。

读取对应的 plan 文件 `data/todo/{plan-name}.md`，理解 plan 的整体设计意图和退出标准。

### Step 3：输出结构化分析

#### 3a. 统计概览

```
## 方法论审计：{plan-name}

### 统计
{X}/{Y} 通过 | {N} 失败 | {M} 异常信号
```

#### 3b. 事实记录（简短）

列出失败任务和异常信号，每条一行。这里只记录事实，不做归因。

```
### 事实
- T{N}：{发生了什么}
- 异常：{什么异常信号}
```

#### 3c. 方法论审计（核心）

这是 review 的核心。从三个维度审视整个 plan 和执行过程：

```
### 审计

#### 退出标准质量
（审视所有任务的退出标准定义方式，而非逐个评判对错）
- 退出标准是否基于可观测行为？还是在预测实现细节？
- 验证命令是否真正验证了退出标准声称的东西？有没有"命令通过 ≠ 标准满足"的情况？
- 有没有任务的退出标准其实是不可验证的（模糊的质量判断、主观偏好）？

#### 任务边界与依赖
- 任务拆分粒度是否合适？有没有太大（子 Agent 迷失方向）或太小（调度开销大于执行）的？
- 跨任务依赖是否显式声明且验证？有没有隐含的假设？
- 并行任务之间有没有未声明的共享状态？

#### 执行纪律
- 流水线在哪些架构边界表现脆弱？
- 哪些"成功"可能是退出标准太弱导致的侥幸？
```

#### 3d. 改进建议

只输出通过准入标准的方法论级建议。**宁可不提也不降级为补丁。**

```
### 改进建议

{如果有值得沉淀的方法论级建议：}

1. **{原则标题}**：{always/never 表述的原则}
   ← 证据：{从哪个具体事实推导出这条原则}

...

---
采纳哪些？（全部 / 逐条选择 / 跳过）

{如果没有方法论级建议（包括全部 PASS 且审计未发现结构性问题）：}

本次执行未发现方法论级改进点。
```

### Step 4：等待用户选择

用户可能回复：
- "全部" → 采纳所有建议
- "1, 3" 或 "第1条和第3条" → 采纳指定建议
- "跳过" → 不采纳任何建议，结束

### Step 5：规则沉淀

用户选择采纳的建议后：

1. 读取 `commands/todo.md`
2. 找到 `## 子任务拆解原则` 区块
3. 在该区块的**最后一条规则之后、下一个 `##` 之前**追加新规则
4. 每条新规则格式为：`- **{规则标题}**：{规则内容}（来自 {plan-name} 方法论审计）`
5. 写回 todo.md
6. 输出确认信息

## 反面示例（不要产出这样的建议）

- ❌ "涉及百分比阈值的退出标准必须先做 5-10 个样本验证" — if-then 补丁
- ❌ "新建文件的 finish 前要检查 untracked files" — 针对具体 bug 的补丁
- ❌ "退出标准中的具体值应标注来源可信度" — 给错误数据贴标签，不解决根因
- ❌ "子 Agent 应该在提交前运行 lint" — 模型能力增强后自然消失的问题

## 正面示例

- ✅ "退出标准始终描述可观测行为（'脚本输出包含 X'），不预测实现结果（'覆盖率 ≥80%'）" — 退出标准的定义哲学
- ✅ "跨版本控制边界的操作必须有显式的协调步骤" — 架构纪律
- ✅ "验证命令的强度必须匹配退出标准的断言强度——如果标准声称'正确实现了 X'，验证不能只检查'文件存在'" — 验证设计原则
